# Deployment Guide

> Generated by a Staff Software Engineer performing a full repository documentation audit.
> Audit date: 2026-06-13

TrackOpenSource is fully containerized for both local development and production environments. It leverages Docker Compose to orchestrate the Next.js frontend, Rust backend, PostgreSQL database, and Redis cache.

---

## 1. Environment Variables

Both local and production environments require configuration via a `.env` file placed in the `backend/` directory (for backend services) and the root directory (for `docker-compose.prod.yml`).

### Required Configuration

```env
# Database & Cache
DATABASE_URL=postgres://postgres:password@db:5432/open_source_radar
REDIS_URL=redis://redis:6379/0

# Authentication (Clerk)
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=pk_test_...
CLERK_SECRET_KEY=sk_test_...
CLERK_WEBHOOK_SECRET=whsec_...
CLERK_PEM_PUBLIC_KEY="-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----"
CLERK_ISSUER=https://...
CORS_ORIGIN=http://localhost:3000  # Or your prod domain

# Data Collection
GITHUB_TOKEN=ghp_...               # Essential for API rate limits

# Alerts (Optional)
DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/...

# E2E Testing (NEVER SET TRUE IN PROD)
# E2E_TEST_MODE=false
```

## 2. Local Development Setup

Local development utilizes hot-reloading for both the frontend (Next.js) and the backend (Cargo Watch + SQLx CLI).

**Key files:**
*   `docker-compose.yml`
*   `backend/Dockerfile.dev`
*   `frontend/Dockerfile.dev`

### Startup Instructions

1.  Create the `.env` file in `backend/.env`.
2.  Start the entire stack:
    ```bash
    docker-compose up --build
    ```

### How Dev Mode Works
*   **Database Migrations:** The `backend/Dockerfile.dev` automatically executes `sqlx database create` and `sqlx migrate run` upon container start.
*   **Hot Reloading:** `cargo-watch` monitors the Rust source files and recompiles the backend gateway (`run --bin backend`) and worker daemon (`run --bin worker`).
*   **API Proxying:** The Next.js frontend runs on `http://localhost:3000`. API calls made to `/api/*` are rewritten via `next.config.ts` to `http://backend:8080/api/*` internally, bypassing CORS issues.

## 3. Production Deployment

Production deployment focuses on security, performance, and isolated networking. The Next.js app is compiled to a standalone binary, and the Rust services are compiled in `--release` mode.

**Key files:**
*   `docker-compose.prod.yml`
*   `backend/Dockerfile`
*   `frontend/Dockerfile`
*   `Caddyfile`

### Startup Instructions

1.  Create a `.env` file in the root directory matching the `docker-compose.prod.yml` interpolations.
2.  Start the production stack in detached mode:
    ```bash
    docker-compose -f docker-compose.prod.yml up --build -d
    ```

### Production Architecture
*   **Caddy Reverse Proxy:** The `Caddyfile` handles automatic TLS certificate provisioning (via Let's Encrypt), HTTP to HTTPS redirection, and injects critical security headers (HSTS, CSP, X-Frame-Options). It is the **only** service that binds to host ports (80, 443).
*   **Network Isolation:** `db`, `redis`, `backend`, and `frontend` containers use the `expose` directive rather than `ports`. They are only accessible via the internal Docker network bridge.
*   **Next.js Standalone:** `frontend/Dockerfile` uses the Next.js `standalone` output mode, creating a minimal Alpine Linux runner image without the massive `node_modules` folder.
*   **Rust Multi-Stage Build:** `backend/Dockerfile` builds all four binaries (`backend`, `collector`, `ranker`, `worker`) in a `rust:bookworm` layer, then copies the compiled binaries into a lean `debian:bookworm-slim` runtime image running as a non-root `appuser`.
*   **Cron Pipeline:** Data collection isn't handled directly by the Docker stack. Instead, a `Jenkinsfile` runs `cargo run --bin collector` daily at `00:00 UTC` against the production database.

## 4. Scaling Recommendations

As TrackOpenSource grows past 10,000 tracked repositories, the deployment architecture will need to scale beyond a single Docker host.

### Phase 1: Vertical Scaling (Current)
*   **Database:** Increase PostgreSQL `shared_buffers` and `work_mem` for analytical queries.
*   **Worker:** The worker daemon is stateless. You can spin up multiple worker containers on the same host to drain the `scan_jobs` queue faster. Because they use `FOR UPDATE SKIP LOCKED`, they will not duplicate work.

### Phase 2: Horizontal Scaling (Future)
1.  **Extract Postgres & Redis:** Move `db` and `redis` to managed services (e.g., AWS RDS, Amazon ElastiCache) to offload I/O and memory pressure from the application host.
2.  **Load Balance the Gateway:** Scale the `backend` container behind a load balancer. The Axum gateway is completely stateless; rate limiting uses the centralized Redis instance, and auth is handled via public JWKS keys.
3.  **Distributed Workers:** Deploy `worker` containers across multiple cheap compute nodes (e.g., spot instances). Ensure they all connect to the same managed PostgreSQL database.
4.  **Static Edge Caching:** Connect Caddy or a CDN (Cloudflare) to cache the Next.js static assets and SSR responses where applicable.
