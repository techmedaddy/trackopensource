# Documentation Audit — TrackOpenSource



---

## 1. Project Overview

**TrackOpenSource** (branded "Open Source Career Radar") is a market intelligence platform that tracks developer adoption vectors and language ecosystem trends across open-source repositories. It combines GitHub activity metrics, HackerNews hiring thread analysis, and social signal aggregation into a unified scoring engine that ranks repositories by momentum rather than raw popularity.

**Target users:** Developers evaluating technology bets, recruiters assessing ecosystem demand, open-source maintainers benchmarking traction.

**Live deployment:** `https://trackopensource.duckdns.org`

## 4. Backend Architecture

### Binaries (4 separate executables)
| Binary | Entry | Purpose |
|--------|-------|---------|
| `trackopensource` (default) | `main.rs` | HTTP API server on port 8080 |
| `worker` | `bin/worker.rs` | Background task daemon (infinite loop) |
| `collector` | `bin/collector.rs` | One-shot GitHub + HN data collection |
| `backtest` | `bin/backtest.rs` | Walk-forward algorithmic validation CLI |

### Route Groups (from `main.rs`)
| Group | Auth Layer | Routes |
|-------|-----------|--------|
| **Public** | None | `GET /` (health), `GET /api/trending`, `GET /api/fastest-growing`, `GET /api/search`, `GET /api/repos/:id`, `GET /api/facets`, `POST /api/webhooks/clerk` |
| **Protected** | Clerk JWT (`require_auth`) | `POST /api/track`, `POST /api/trigger`, `GET /api/watchlists`, `POST /api/watchlists/:id`, `DELETE /api/watchlists/:id`, `GET /api/keys`, `POST /api/keys`, `DELETE /api/keys/:id` |
| **V1 (API Key)** | SHA-256 key + Redis rate limit (`require_api_key`) | `GET /api/v1/trending`, `GET /api/v1/fastest-growing`, `GET /api/v1/repos/:id` |

### Data Collection Pipeline (`collector.rs`)
1. Load tracked repos from DB (`WHERE is_tracked = true`)
2. Discover new momentum repos via GitHub Search API (48h + 7d velocity buckets)
3. Discover top frameworks per language (8 languages × 65 repos)
4. Deduplicate, then stream-process with `buffer_unordered(5)`
5. For each repo: fetch GitHub metadata → upsert `repositories` → insert `snapshots` → fetch HN mentions → save `social_mentions`
6. Run HN hiring thread scraper (`jobs.rs`) → match via PostgreSQL `tsvector` against repo aliases

### Ranking Engine (`ranking.rs`)
- Runs across 3 windows: 7, 30, 90 days
- Computes raw metrics: `star_velocity`, `growth_ratio`, `contributor_growth`, `activity_raw`, `social_raw`, `hiring_raw`
- Normalizes all metrics to 0–100 using `max(cohort)` as denominator
- Default trend_score formula: `velocity×0.30 + growth×0.15 + contributor×0.15 + hiring×0.20 + social×0.15 + activity×0.05`
- User-provided weights override via query params (must sum to 1.0)

### Worker Queue (`worker.rs`)
- Infinite loop polling `scan_jobs` with `FOR UPDATE SKIP LOCKED`
- Supports job types: `collect`, `rank`, `full`, `hiring_scan`
- Updates status to `done` or `failed` with error message
- Sleeps 5s when queue is empty

## 8. Authentication Flow

### Clerk JWT (Browser Sessions)
1. User signs in via Clerk at `/sign-in`
2. Next.js middleware (`clerkMiddleware`) protects non-public routes
3. Frontend attaches `Bearer <JWT>` header to protected API calls
4. Axum `require_auth` middleware extracts token, verifies RS256 signature against `CLERK_PEM_PUBLIC_KEY`, validates `iss` (issuer) and `azp` (authorized party)
5. Claims (`sub`, `exp`, `iss`, `azp`) injected into request extensions

### API Key (Programmatic Access)
1. User creates key via `POST /api/keys` → receives `osr_<32chars>`
2. Client sends `x-api-key: osr_...` header
3. Axum `require_api_key` middleware hashes key (SHA-256), looks up in `api_keys` table, updates `last_used_at`
4. Redis sliding window rate limit: 100 requests/60 seconds per user

### E2E Test Bypass
- `E2E_TEST_MODE=true` on backend: accepts `mock-clerk-jwt-token` as valid
- `NEXT_PUBLIC_E2E_TEST_MODE=true` on frontend: skips `auth.protect()` in middleware
- **CRITICAL:** Must be absent from production environment

## 10. Deployment Architecture

### Development (`docker-compose.yml`)
5 services: `db`, `redis`, `backend` (cargo-watch), `worker` (cargo-watch), `frontend` (next dev)
All ports exposed to host.

### Production (`docker-compose.prod.yml`)
6 services: `db`, `redis`, `backend`, `worker`, `frontend`, `caddy`
Only Caddy exposes ports 80/443. All other services use `expose` (internal only).
Caddy handles: TLS auto-cert, HSTS, CSP, X-Frame-Options, reverse proxy to `frontend:3000`.
Frontend proxies `/api/*` to `backend:8080` via Next.js rewrites.

### CI/CD (`Jenkinsfile`)
Daily cron at 00:00 UTC → checkout → setup Rust → `cargo run --bin collector`
